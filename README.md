# Ecommerce

Spring Boot 기반 Ecommerce 백엔드 프로젝트입니다.

이 프로젝트는 완성된 커머스 서비스를 만드는 것보다, Spring 기반 백엔드 애플리케이션의 주요 흐름을 직접 구현하며 내부 동작을 이해하고, 주문 처리 과정에서 발생할 수 있는 동시성·트랜잭션·비동기 처리 문제를 경험해보기 위해 진행했습니다.

특히 단순 CRUD 구현에 그치지 않고, 한정 수량 상품 주문 상황에서 발생한 재고 정합성 문제, 데드락, 커넥션 타임아웃, 비동기 결제 작업 제어 문제를 직접 재현하고 개선하는 데 집중했습니다.

## 핵심 경험

### 1. 한정 수량 상품 동시 주문 처리 안정화

한정 수량 1000개 상품에 대해 1000건의 동시 주문 상황을 테스트했습니다.

초기에는 재고 차감, 결제 대기, 주문 생성, 매출 반영을 하나의 트랜잭션에서 처리했습니다.  
그 결과 전체 요청의 90% 이상에서 데드락과 커넥션 대기 타임아웃이 발생했고, 재고 정합성 문제도 확인했습니다.

이를 해결하기 위해 주문 처리 시 가장 먼저 상품 row에 대한 비관적 락을 획득하도록 변경했습니다.  
또한 결제 대기 시간을 주문 트랜잭션에서 분리해, 주문 트랜잭션에서는 재고 차감과 `PENDING_PAYMENT` 주문 생성까지만 처리하도록 개선했습니다.

그 결과 동시 주문 상황에서도 요청을 안정적으로 처리하고 재고 정합성을 확보할 수 있었습니다.

<br>

### 2. 비동기 결제 처리 구조 개선

처음에는 주문 요청이 들어오면 결제 작업을 바로 `ThreadPoolTaskExecutor`에 제출했습니다.

하지만 요청이 몰릴 경우 executor의 처리 한계를 넘어 작업이 계속 제출될 수 있었고, reject가 발생할 수 있었습니다.  
또한 결제 작업이 메모리에만 존재해 서버 장애 시 작업이 유실될 수 있는 문제가 있었습니다.

이를 개선하기 위해 결제 이벤트를 먼저 DB에 저장하고, 단일 디스패처가 DB에서 이벤트를 읽어 executor에 전달하는 구조로 변경했습니다.  
또한 세마포어를 사용해 executor가 감당할 수 있는 수만큼만 작업을 제출하도록 제한했습니다.

이를 통해 결제 작업이 무제한으로 push되는 문제를 막고, 장애 발생 시에도 재처리 가능한 구조를 확보했습니다.

## 배운 점

이 프로젝트를 통해 단순히 기능을 구현하는 것과 안정적으로 처리하는 것은 다르다는 점을 배웠습니다.

특히 주문 기능을 개선하면서 다음 내용을 직접 경험했습니다.

- 트랜잭션 안에 오래 걸리는 작업을 포함하면 커넥션 점유 시간이 길어질 수 있음
- 동시 요청 상황에서는 락 획득 순서와 트랜잭션 범위가 중요함
- 비동기 처리는 단순히 executor에 넘기는 것이 아니라 작업 제출 속도도 제어해야 함
- 메모리 기반 작업 큐는 장애 시 유실 가능성이 있으므로 복구 가능한 구조가 필요함
- Spring, JPA, DB lock, executor의 동작 방식을 이해해야 문제 원인을 추적할 수 있음

<br>

## 정리

이 프로젝트는 Ecommerce 도메인을 통해 Spring 기반 백엔드의 주요 흐름을 학습하고, 주문 처리 과정에서 발생할 수 있는 기술적 문제를 직접 경험하기 위해 진행했습니다.

완성된 서비스보다는 문제 상황을 재현하고, 원인을 분석하고, 구조를 개선하는 과정에 초점을 두었습니다.  
이를 통해 트랜잭션 설계, 동시성 제어, 비동기 처리, 작업 제출 제어, 장애 복구 가능성에 대해 고민해볼 수 있었습니다.
